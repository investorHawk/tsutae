# 化学療法中の症状ジャーナル 構成案(2026-11-03)

対象大会: Built with Claude (Code): Japan 2026(〜11/10 14:00 JST、ソロ、公開リポジトリ必須)。残り約7日。

## 1. 一言で

化学療法中の患者が毎日、短い**クローズクエスチョン**と自由記載・音声の**オープンクエスチョン**に答える。Claude がその記録を「何月何日(何コース目の何日目)から、どの症状が、どの程度」という時系列に直し、**医師が事前に決めた形式**の紙の症状レポートにして、受診時に医師の手元へ印刷する(患者が院内のQRコードを読むと印刷される。4.5節)。

- **基本方針(2026-11-03 ユーザー)**: 患者主導のまとめは医師が読むのに時間がかかり嫌われる。**医師が欲しい情報を、医師の形式で**出すことを最優先にする

- **困っている人**: 外科医本人。現状は、外来で患者の話がまとまらず、オープンとクローズの質問を繰り返しながら症状を確認している(2026-11-03 ユーザー確認)
- **何が変わるか(2026-11-03 ユーザーの実感値、未測定)**: 患者1名の症状の聞き取りが **約3分 → 約30秒** になる。加えて**問診の抜けが減る**。患者は日付を正確に覚えていなくても伝わる
- **テーマ**: テーマ1(外科医本人の外来)とテーマ2(つらくて言えなかった・忘れた症状が医師に届いていなかった患者)の両方に当たる
- **範囲**: 消化器がんの化学療法中の副作用に限る。末期・緩和ケアは対象外

## 2. 既存との違い

| 既存 | 形 |
|---|---|
| Welby マイカルテ ONC(阪大で2021-23年に検証) | 治療日誌アプリ。資料に「ePROは日常臨床には未だ普及していない」とある |
| 慶應 LINE型ePRO | CTCAEに基づく質問に、重さを選んで返信する |
| AmbuFlex(デンマーク) | PRO-CTCAEの回答をグラフにして腫瘍医に見せる |
| eChemoCoach(オランダ) | 症状入力と、患者への自己管理の助言 |

既存品は**決まった質問に段階で答える形**が中心。3つの臨床試験の解析では、患者の58%が自由記載欄にも書き込んでいた。その多くは後から標準用語に当てはめられたが、当てはめは事後に人が行っており、著者は「リアルタイムで当てはめる余地がある」と書いている(PMC6402312)。

**違い**: クローズ回答と自由記載・音声を組み合わせ、自由記載を Claude が「日付・コースの日数・標準用語・元の文の引用」つきの時系列に直す。さらに医師が自然言語で決めた形式で出す。
### 先行調査のやり直し(2026-11-03)

**最初の結論を訂正する。** 「声や文章で記録し、AIが時系列に整理して医師向けの要約を作る」アプリは、慢性疾患向けにすでにある。

| 種類 | 例 | この案との違い |
|---|---|---|
| 一般向けのAI症状日記 | [Juno](https://junocompanion.com/)(声と文章のAIチャット → 時系列 → 医師向けの1枚の要約。患者と会話し助言する)、[LogSymptoms](https://logsymptoms.com/)(声と文章 → 構造化した時系列、受診メモ。助言はしない)、CareClinic、Bearable | 患者側の道具。化学療法の治療コースの考え方も、医師が決める形式もない |
| がん領域のePRO | Welby ONC、ヒビログ、P-Guardian、eReQo、慶應LINE、Kaiku、Noona、CANKADO | 決まった質問とアラート。LLMで自由記載を処理するものは確認できなかった |
| LLM×化学療法の研究 | [NCT07198581](https://clinicaltrials.gov/study/NCT07198581)(韓国。医療者が症状を入力し、LLMが対処を推奨)、[NCT07273812](https://clinicaltrials.gov/study/NCT07273812)(イラク。患者向けに助言とアラート)、[Cancers 2024](https://doi.org/10.3390/cancers16162830)(毒性の分類) | 入力者・出力の向きが違う、または患者に助言する |

注意すべき誤り: IBDの研究で、LLMが軽い症状や改善中の症状を「症状なし」と分類しやすいと分かっている([PMC11398594](https://www.ncbi.nlm.nih.gov/pmc/articles/PMC11398594/))。

**この案だけの点(デモの冒頭で示す)**
1. 化学療法の治療コースに合わせる(コース何日目に直し、前のコースと同じ日数で比べる)
2. 医師側が設定する(レジメン別の質問集、医師別の要約形式)
3. 欠けた記録を情報として扱う(「つらくて書けない」のタップ、空白の並び方)
4. クローズ回答と自由記載の食い違いを見つける
5. 患者の画面にAIの文を出さない

「AIの症状日記 → 医師向け要約」とだけ見えると、Juno がすでにあるので新規性で負ける。

## 3. AIの仕事(重くなるようにする)

1. **相対的な時間表現を日付に直す**: 「点滴の次の日から」「おととい」「先週の木曜まで」を、記録日とレジメンの投与予定から暦日に直し、コースの何日目かも付ける
2. **症状を標準用語に当てはめる**: 元の文の引用を必ず付ける(例: 「指先がピリピリ」→ 末梢神経障害)
3. **クローズ回答と自由記載を突き合わせる**: 「下痢なし」と答えた日に「水っぽい便」と書いていたら、**解決せずに**食い違いとして示す
4. **前のコースとの変化を出す**: 同じコースの日数で並べて比べる
5. **体調不良時の聞き取りにくい音声書き起こしを解釈する**: 言いよどみや認識の誤りを含む書き起こしから出来事を取り出す。確信度が低いものはそう示す
6. **医師が決めた形式でまとめる**: 医師ごとの要約形式で表示する

## 4. 入力の設計(ユーザーの懸念2点への答え)

### 懸念1: 体調が悪いと音声入力がうまく働かない
入力を段階に分け、**最低限はワンタップ**で済むようにする。

| 段階 | 内容 | 体調が悪い日 |
|---|---|---|
| 0 | 「今日はつらくて書けない」ボタン1つ。**このタップ自体を記録する** | これだけで終了できる |
| 1 | クローズクエスチョン3〜6問(大きなボタン、レジメンごとに医師が設定) | 可能なら |
| 2 | オープンクエスチョン(自由記載か音声) | 任意 |

- **家族による代理入力**を認め、代理と表示する
- 調子の良い日に「書けなかった日に何があったか」を後から入力できるようにし、**回想**と表示する(医師に記憶の正確さの違いが分かるように)

### 懸念2: つらい日ほど入力しないので偏りが出る
欠けた記録を「症状なし」とみなさず、**情報として扱う**。

- 未入力日を「症状なし」で埋めない。経過表に空白として表示する
- 「入力なし」「つらくて書けない(タップあり)」「症状なし(回答あり)」の3つを区別する
- 欠けた日の並び方を医師に示す(例: 毎コース3〜5日目が空白)。重い日の手がかりになる。これは機能として売り込む

## 4.5 受診時の受け渡し: QRコードで医師の手元に印刷(2026-11-03 ユーザー案)

**流れ**
1. 患者が受診時に、院内に掲示されたQRコードをスマホで読み、指定のURLを開く
2. 直近の記録から、医師が指定した形式の症状レポートが作られる
3. レポートは**患者のスマホには表示されず**、医師の手元(診察室か外来のプリンタ)に印刷される

**この方式の利点**
- **電子カルテとつながずに済む。** 国内のePROは電子カルテとの連携が導入の壁とされている。紙を介すれば、閉じたネットワークのカルテ端末に触れずに、医師の机に届く
- **患者はAIの文を見ない。** 5節の「患者の画面にAIの文を出さない」が、仕組みとして自然に守られる
- **医師にとっての使いやすさ。** 慣れた紙で、毎回同じ形式で出てくる。Juno などの「患者が持ってくる要約」との最大の違いになる
- **デモ映え。** QRを読む → プリンタから医師形式のレポートが出る、が10秒で伝わる

**詰めること**
- **誰のレポートか**: AIには氏名を送らないので、氏名との結び付けは院内の紙の上だけで行う。案: QRを読んだ時に、患者が院内のページで受付番号か診察券番号を入れる。その番号はレポートの印刷時に院内で付けるだけにし、Claude には送らない
- **印刷の経路**: カルテ端末はインターネットに出られない前提(NCD案での確認)。院内にカルテ網とは別のインターネット回線の「印刷用端末」を置き、印刷ジョブを取りに行く小さな常駐プログラムを動かす。デモでは、PCのブラウザでの印刷(PDF)で代用する
- **生成にかかる時間**: QRを読んでから Claude を呼ぶと数十秒かかる。前夜にまとめを作っておき、QRの時点では最新分だけを足す
- **患者が自分の記録を見る権利**: 患者は自分の生の記録(入力したもの)はいつでも見られる。見られないのはAIのまとめだけ、と説明する

## 5. 責任の線引き(審査で必ず聞かれる)

**AIがしないこと**
- 重さの判定はしない。出すのは候補だけで、元の文の引用を必ず並べ、医師が確定する
- トリアージや受診判断はしない
- **患者の画面にAIが生成した文を出さない。** 患者側の表示は定型文だけにする。モデルが生成した文字列が患者の画面に届く経路を Hook で止める

**緊急時(例: 「38度の熱」が記録されたが、受診は来週)**
- AIには判断させない
- レジメンの Skill に**施設が書いた固定の規則**(例: 発熱の回答があれば施設の連絡先の定型文を表示)を持たせ、決まったとおりに表示する。判断しているのは医師が書いた規則で、モデルではない
- 受診と受診の間に医療機関へ通知するのは、責任を伴う見守りサービスになる。**対象外**とし、施設が決めることとして README に書く

## 6. 医師が設定するもの(Skill 2種、どちらも自然言語で設定)

1. **レジメンごとのクローズクエスチョン集**
   - 例: FOLFOX / CAPOX → 末梢神経障害、手足症候群、下痢、口内炎、悪心、食欲、発熱
   - 緊急時の固定規則もここに置く
2. **医師ごとの要約形式**
   - 例: 「コース日数の横軸で、Grade候補2以上だけ太字に、食い違いは先頭に」

## 7. Claude の使い方(配点25%)

**方針(2026-11-03 変更)**: Skill・サブエージェント・Hook を FastAPI 内で自作しない。**変換パイプラインを Claude Agent SDK の上に作り**、Claude Code の機能そのものとして見せる(自作の仕組みは「普通のプログラム」と見られる)。Agent SDK で hooks / subagents / skills が使えることは実装前に要確認。

| 機能 | 役割 |
|---|---|
| Skills(`.claude/skills/`) | レジメン別の質問集と固定規則、医師別の要約形式 |
| サブエージェント | 時間表現を日付に直す役/標準用語に当てはめる役/クローズと自由記載を突き合わせる役。統合役がまとめる |
| Hooks(PreToolUse / PostToolUse) | (1) 患者の画面へモデル生成文を出さない (2) 引用のない症状の記載をレポートに出さない (3) 伏せ字にしていない識別子らしき文字列があれば Claude への送信を止める |
| Claude Code | 開発そのものを Claude Code で行い、公開コミットとテスト件数で示す |
| MCP(余力) | 印刷用端末を MCP サーバーにする |

**目玉(デモの山場の1つ)**: 医師が自然言語で言うと Skill が書き換わり、次のコースから質問とレポートが変わるループ。例: 診察後に「口内炎は、食事がとれたかも次から聞いて」→ Claude Code が Skill を更新 → 翌日の患者の質問とレポートの列が変わる。

## 8. 個人情報

- カルテではないが、要配慮個人情報にあたる。本人の同意を取り、送る情報を最小にする。デモは合成データで行う
- **患者情報は削除してから Claude に送る(2026-11-03 ユーザー)**: アプリはそもそも氏名・生年月日を集めない(仮名IDで管理)。自由記載に混ざる氏名・電話番号・病院名・地名などは、送る前に手元の規則で伏せる。氏名との結び付けは、院内で印刷する時だけ行う(4.5節)
- **音声入力**: Chrome の Web Speech API は、標準では音声を Google のサーバーに送って認識する(MDN)。オンデバイス認識は Chromium で出荷が提案されているが、日本語で使えるかは未確認
  - 対策: (a) オンデバイスで日本語が使えれば採用する (b) 使えなければ、ブラウザ内やローカルの文字起こし(Whisper系)を代わりの選択肢として検討する。実装前に確認する
- **PRO-CTCAE 日本語版**(東北大・東大・JCOGが作成し、NCIが承認): 利用条件は未確認。質問の文言を使う前に NCI の公式サイトか JCOG に確認する。確認できるまでは独自の文言で作る

## 9. 7日間のスコープ(React + FastAPI + SQLite)

MVP = 患者用スマホWeb(タップ/クローズ/自由記載。**音声は MVP から外す**)→ 氏名などを伏せて Agent SDK で変換 → QRで医師の手元に医師形式の紙レポート(経過表+要約+引用、HTML印刷CSS → ブラウザ印刷)

落としたもの(2026-11-03): 音声入力(Web Speech API は音声を Google に送るため個人情報方針と矛盾。つらい日の答えはワンタップで成立)、PWA 化。

| 段階 | 内容 | 区分 |
